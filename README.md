# Mobile Repair Cost Estimator

A public, anonymous mobile phone repair cost estimator. No login, no
account, no personal information — pick a device, describe the problem,
answer a few condition questions, and get an estimated repair cost range.

This project has two completely separate applications:

- **`backend/`** — Python + FastAPI. Owns all pricing/estimation logic and
  data, served as a JSON REST API.
- **`frontend/`** — React + Vite. Talks to the backend only over HTTP
  (`frontend/src/api/api.js`). It contains no pricing logic of its own.

```
React (frontend) → HTTP request → FastAPI (backend) → estimator service → pricing/device JSON → JSON response → React result screen
```

## 1. What you need installed (macOS)

- **Python 3.10+** — check with `python3 --version`
- **Node.js 18+** and **npm** — check with `node --version` and `npm --version`
- **VS Code** (or any editor)

If you don't have Python or Node, install them from [python.org](https://www.python.org/downloads/)
and [nodejs.org](https://nodejs.org/) first.

## 2. Open the project

1. Unzip `MobileRepairCostEstimator.zip`
2. Open the extracted folder in VS Code: `File → Open Folder…`

You should see `backend/`, `frontend/`, this `README.md`, and `.gitignore`
at the top level.

---

## 3. Run the backend (FastAPI)

Open a terminal in VS Code (`` Terminal → New Terminal ``) and run:

```bash
cd backend

# create a virtual environment
python3 -m venv venv

# activate it (macOS/Linux)
source venv/bin/activate

# install dependencies
python3 -m pip install -r requirements.txt

# (optional) copy the example env file and adjust it if needed
cp .env.example .env

# start the API with auto-reload
python3 -m uvicorn backend:app --reload
```

You should see Uvicorn start on `http://127.0.0.1:8000`. Leave this
terminal running.

**Verify it's working:** open [http://localhost:8000/api/health](http://localhost:8000/api/health)
in your browser — you should see `{"status":"ok", ...}`. Interactive API
docs are auto-generated by FastAPI at
[http://localhost:8000/docs](http://localhost:8000/docs).

---

## 4. Run the frontend (React + Vite)

Open a **second** terminal (keep the backend running in the first one):

```bash
cd frontend

npm install

# (optional) copy the example env file and adjust it if needed
cp .env.example .env

npm run dev
```

Vite will print a local URL, normally `http://localhost:5173`. Open that
in your browser.

## 5. Using the app

1. **Device** — search or filter by brand, tap a device.
2. **Problem** — select one or more issues (multi-select).
3. **Condition** — answer a short, issue-specific set of questions (every
   ambiguous question includes a "Not sure" option).
4. **Estimate** — the frontend calls `POST /api/estimate` and shows the
   returned price range, a cost breakdown, a confidence level with plain-
   language reasoning, a repair-vs-device-value comparison, and a
   share/copy action.

If the backend isn't running, the frontend will show a friendly
"couldn't reach the estimator service" message instead of a raw network
error — start the backend and click **Try again**.

## 6. API reference

All responses are JSON. Base URL: `http://localhost:8000`.

| Method | Path                  | Purpose                                   |
|--------|-----------------------|--------------------------------------------|
| GET    | `/api/health`         | Health check                               |
| GET    | `/api/brands`         | List of supported brands                   |
| GET    | `/api/devices`        | List devices (optional `?brand=` `?search=`) |
| GET    | `/api/devices/{id}`   | Single device                              |
| GET    | `/api/repairs`        | List repair categories + their questions   |
| GET    | `/api/repairs/{id}`   | Single repair category                     |
| POST   | `/api/estimate`       | Calculate an estimate                      |

### `POST /api/estimate`

Request:

```json
{
  "device_id": "apple-iphone-13",
  "repair_ids": ["screen"],
  "answers": {
    "screen": {
      "display_working": "yes",
      "touch_working": "yes",
      "damage_type": "glass_only"
    }
  },
  "region": "delhi",
  "device_value_override": null
}
```

`repair_ids` accepts more than one category if the user selected multiple
problems — `answers` is then keyed by each repair id. `region` and
`device_value_override` are optional.

Response:

```json
{
  "device_id": "apple-iphone-13",
  "device": "Apple iPhone 13",
  "repairs": ["Screen & Display"],
  "repair_items": [
    {
      "repair_id": "screen",
      "name": "Screen & Display",
      "likely_repair": "Outer glass replacement",
      "confidence": "high",
      "minimum": 8000,
      "maximum": 12000,
      "note": null
    }
  ],
  "currency": "INR",
  "minimum": 8400,
  "maximum": 12600,
  "repair_time": "1 – 3 hours",
  "confidence": "high",
  "likely_repair": "Outer glass replacement",
  "breakdown": { "parts_min": 6552, "parts_max": 9828, "labor_min": 1848, "labor_max": 2772 },
  "region": "delhi",
  "device_value_estimate": 38000,
  "repair_vs_value_pct": 27.6,
  "disclaimer": "Estimate only. ..."
}
```

## 7. Changing pricing data

All pricing lives in **`backend/database/pricing.json`**, organized by
repair type and device *tier* (`budget` / `mid` / `flagship`) rather than
one row per device — this mirrors the tier-based logic that was already in
the original prototype, and avoids hundreds of near-duplicate rows. Each
repair type has a `[min, max]` range per tier:

```json
"screen": { "budget": [2500, 4500], "mid": [4500, 8000], "flagship": [8000, 16000] }
```

Edit these numbers directly — no code changes needed. The file also holds
the labor-share percentage and the regional price multipliers.

**The current numbers are a sample/illustrative dataset, not verified
market prices.** Replace them with sourced Indian repair-market pricing
before using this for anything real. Nothing in the code assumes the
numbers are accurate.

## 8. Adding a new phone

Edit **`backend/database/devices.json`** and add an entry:

```json
{
  "id": "samsung-galaxy-s24",
  "brand": "Samsung",
  "model": "Galaxy S24",
  "tier": "flagship",
  "approx_value_inr": 55000
}
```

- `id` should be unique (a simple slug works).
- `tier` must be one of `budget`, `mid`, `flagship` — it determines which
  pricing row from `pricing.json` applies.
- `approx_value_inr` is used for the repair-vs-device-value comparison and
  is optional.

Restart the backend (or just save — `--reload` picks it up automatically)
and the new device will appear in device search.

---

## 9. Adding a new repair category

Edit **`backend/database/repairs.json`** and add a new object with an
`id`, `name`, `examples` string, and a `questions` array (same shape as
the existing categories — each question has a `key`, `label`, and a list
of `options`, each with a `value`/`label` and an optional `sub` line).
Then add a matching entry to `tier_pricing` in `pricing.json` using the
same `id`, and a branch in `estimate_category()` inside
`backend/services/estimator.py` that interprets the new question answers
(confidence level, likely-repair text, and any range adjustments). This is
the one place that genuinely requires a small code change, since it's
where the "how do these answers affect the price" logic lives.

## 11. What was migrated from the original artifact vs. changed

**Migrated as-is:**
- Visual design — colors, typography (Manrope + IBM Plex Mono), the
  segmented progress indicator, card/pill/chip styles, layout, spacing.
- The full user flow: device search/filter → multi-select problems →
  per-category dynamic questions → result screen.
- All device, repair-category, question, and tier-pricing sample data.
- The estimation logic itself (per-category confidence rules, range
  adjustments, the "not sure" handling, the multi-issue labor-overlap
  discount) — ported line-for-line from JavaScript into
  `backend/services/estimator.py`.
- The result screen's content: price range, breakdown table, confidence
  explanation, repair-vs-device-value comparison, disclaimer, share/copy.

**Changed for the new architecture:**
- The estimation math now runs on the backend and is reached over HTTP —
  the frontend only renders whatever the API returns.
- Region selection sends a region id to the backend, which applies the
  multiplier server-side (previously done in the browser).
- Device search is loaded from the API once and filtered client-side for
  responsiveness (the same UX as the original), rather than issuing a
  network request per keystroke.

## 12. Known limitations / sample data to replace

- **Pricing is illustrative, not verified.** All figures in
  `pricing.json` need to be replaced with real, sourced Indian repair
  market data before this is used for anything beyond a prototype.
- **Device catalog is small** (28 devices across 9 brands) — intended as
  a starting set per the original spec, meant to be expanded.
- **`approx_value_inr`** (used for the repair-vs-device-value comparison)
  is a rough illustrative figure per device, not a live market value feed.
- **No persistent database yet** — data is read from JSON files on disk,
  as specified for this MVP. An admin dashboard, SQL database, and
  region-aware pricing beyond the current flat multipliers are all called
  out as future work in the original spec and are not implemented here.
- **No automated test suite** — the estimator logic was manually verified
  against the original JS behavior during development, but there are no
  unit tests included yet.
- `docker-compose.yml` was intentionally left out — the two dev servers
  above are simple enough that a container setup didn't add real value
  for local development. Happy to add one if you want a one-command
  Docker-based run later.

## 13. Troubleshooting

- **"We couldn't reach the estimator service"** in the browser — the
  backend isn't running, or `frontend/.env`'s `VITE_API_URL` doesn't match
  where it's running. Confirm `http://localhost:8000/api/health` loads.
- **CORS error in the browser console** — check `backend/.env`'s
  `CORS_ORIGINS` includes the exact origin Vite printed (default
  `http://localhost:5173`), then restart the backend.
- **`uvicorn: command not found`** — make sure the virtual environment is
  activated (`source venv/bin/activate`) before running the server
  command, or use `python3 -m uvicorn backend:app --reload` as shown
  above, which doesn't rely on `uvicorn` being on your PATH.
